# Pocket Clipboard 1.0.4：性能排查与问题清单

日期：2026-10-16（Asia/Shanghai）。检查范围：正在运行的 macOS 接收器、Android 客户端、图片中继服务、安装包与下载站。下面 10 项已完成代码修复；验证范围和限制单独列出。

## 实测结果

- 修复前：PocketClipboard PID 558 每 2 秒接收约 592,374 字节，入站平均约 296,187 B/s，约 1.07 GB/小时。CFNetwork 连续记录完整响应约 590,592 字节、HTTP 200、无缓存命中；来源为每 2 秒下载完整 Base64 图片，下载后才按时间戳去重。
- 新客户端搭配旧服务端、房间已有图片：连续 13 秒实测入站 1482 字节、出站 408 字节，总计约 145.38 B/s。真实上传一张 522,738 字节的合成 PNG 后，安装的接收器写入剪贴板，解码后的像素 SHA256 一致；接下来 8 秒没有重复写入，之后恢复原剪贴板。
- 最终客户端与服务端：连续 13 秒空闲采样，入站 360 字节、出站 714 字节；总计约 82.62 B/s，入站约 27.69 B/s。CFNetwork 显示稳定的 HTTP 304；浏览器验证 304 响应体为 0 字节。这是短时空闲样本，不是全天流量估计；新图片本身仍需正常下载。
- 正常退出后观察 12 秒，进程未自动重启；随后明确启动接收器供继续使用。LaunchAgent 的 KeepAlive 为 false，原有 RunAtLoad 偏好保留。

## 已修复的问题

| 编号 | 优先级 | 问题及影响 | 修复 |
| --- | --- | --- | --- |
| PC-01 | P1 | Mac 每 2 秒取完整图片，即使没有新图片也持续占用带宽与解析 CPU。属于本次实际观测到的异常。 | 先请求元数据并带 ETag / If-None-Match；未变化返回 304。仅新时间戳下载完整图片，成功复制后推进游标。 |
| PC-02 | P2 | 应用每次启动重写 KeepAlive=true，手工禁用自动重启会再次失效。 | 写入 KeepAlive=false，同时保留已有 RunAtLoad 偏好；卸载并重新加载实际 LaunchAgent，使运行状态生效。 |
| PC-03 | P1 | Android 先完整解码相机原图，再缩小；48MP 的 ARGB 像素本身约需 192 MB，UI 预览又读取原图。容易产生内存峰值与卡顿。 | 先只读尺寸，再按采样率解码到最长边不超过 2200；后台生成小预览，主线程只展示 Bitmap。192 MB 为像素大小估算，未在手机上实测。 |
| PC-04 | P2 | Mac 的 JSON、Base64 解码及剪贴板图片处理在主线程执行；接收窗口另有永久 0.5 秒 UI 定时器。 | 在 URLSession 工作队列解码并生成 PNG，主线程只写剪贴板和更新界面；改为状态变化时更新 UI。对极大图片采用最长边 4096 的有界解码。 |
| PC-05 | P1 | 服务端图片/房间缺少总量限制；GET 轮询不断刷新 touched，使旧图片一直占用内存。风险来自实现路径，而非宣称生产已发生 OOM。 | 图片独立按上传后 30 分钟过期；活动配对可继续存在。图片 Base64 缓冲区合计 64 MiB、房间最多 512；容量满明确返回 503，保留现有图片。 |
| PC-06 | P2 | Android 每次发送新建线程，使用可变共享 URI 和后台读取 UI；并发发送可能堆积内存、错用照片。失败路径不保证断开 HTTP 连接。 | 一个工作线程，一次只处理一张，锁定发送按钮；发送前固定 URI、配对码和 Token；连接与图片资源在 finally 中释放，Activity 销毁时取消工作。 |
| PC-07 | P2 | Mac 刷新配对码不取消旧请求；旧回调可能覆盖新会话。请求可能长时间等待，网络和图片失败没有完整的退避策略。 | 显式取消旧任务、会话代次校验、单次调度定时器；请求/资源超时 15/30 秒，失败按 2/4/8/16/30 秒退避，404 自动重新配对。完整图片失败的退避不会被成功的元数据请求重置。 |
| PC-08 | P2 | 服务端重复 JSON 序列化整张 Base64；静态下载先将整个文件读入内存。慢图片下载还可保留已被替换的旧图片缓冲区。 | 图片只编码一次；元数据与 Base64 分开输出；静态文件使用流与背压，完整图片并发下载最多 8 个。 |
| PC-09 | P2 | 上传、图床归档和 SSE 连接缺少并发约束；慢事件流可积压写缓冲。 | 上传最多 4 个、归档 4 个；事件流每房间 8 个、合计 128 个，带心跳与断开清理，积压时断开慢连接。归档容量满时仍允许正常接收图片，明确显示归档失败。 |
| PC-10 | P2 | 较旧的图床上传失败回调会把新图片标成失败；相同毫秒内的上传还可能共用时间戳。 | 归档成功与失败均校验房间和图片身份；时间戳保证递增。旧任务不得覆盖新图状态。 |

P1 表示本次优先处理的流量/内存风险；P2 为请求生命周期、响应性、资源处理及相关正确性问题。上述资源配额不等同于 RSS 硬上限；运行时、活动传输、归档和解码本身仍会占内存。

## 验证与交付

- 服务端 8 项自动回归：原图字节往返、304 空响应、图片独立过期、房间/总内存限额、上传取消释放、SSE 限额与清理、归档并发和旧回调隔离、流式下载及慢读者限制。本机 Node 25 与服务器 Node 20 均通过。
- Mac 7 项回归：新图只下载一次、归档状态变化不重复下载、下载失败可重试、断网退避、刷新取消旧回调、过期房间重新创建、图片持续失败保留退避。最终全部通过。
- macOS 优化构建与临时签名校验通过；本机安装位置 `~/Applications/Pocket Clipboard.app`，版本 1.0.4 / build 5；两个本地构建目录也已同步。
- Android assembleDebug 与 APK 签名检查通过，版本 1.0.4 / versionCode 5。当前没有连接 Android 设备，未验证真机相机行为、后台切换及实际内存峰值；手机需自行安装新版 APK。
- 线上 `pocket-clipboard.service` 正常运行；HTTP/HTTPS 和本机 Caddy 路由探测通过；浏览器核对版本、API 304 与页面资源，新页面无控制台错误。安装包与源码包已在现有下载站更新，公网下载 SHA256 已核对。
